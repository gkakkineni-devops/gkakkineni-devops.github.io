The situation

Deep learning workloads need GPUs, and GPUs are both expensive to leave idle and painful to wait for. Data scientists want capacity on demand; the budget wants nothing running that isn’t doing work.

On top of training, the teams were moving toward LLM-based applications, which bring their own deployment and serving needs.

What I built

  • Orchestrated GPU and TPU-enabled clusters for deep learning workloads across AWS and GCP.
  • Designed Terraform-based pipelines to provision GPU clusters for training, so capacity is created the same way every time.
  • Automated resource monitoring and scaling for GPU workloads, so clusters grow for a job and shrink after it.
  • Integrated SageMaker, Bedrock and Hugging Face into the DevOps pipelines and worked with data scientists and ML engineers to deploy LLM-based apps to production.

How it flows

  1. Training job queued
  2. Scale up GPUs
  3. Train and track
  4. Register model
  5. Deploy and serve
  6. Scale down

Decisions I made and why

Scale on the work, not the calendar

Scaling GPU capacity around the actual jobs, instead of keeping a fixed fleet warm, is where most of the savings came from.

Provision GPU clusters from Terraform

GPU node pools have a lot of details that are easy to get wrong by hand: drivers, instance types, quotas. Defining them in code made them repeatable and reviewable.

Use managed ML services where they fit

SageMaker, Bedrock and Hugging Face cover a lot of ground. Plugging them into the existing pipelines was faster and safer than rebuilding what they already do.

What changed

Training and inference ran up to 30% faster, and automated scaling cut costs for GPU workloads by 15% while keeping performance where it needed to be.

What I’d do next
