The situation

Security checks happened late in the process, so issues were found after code was already on its way to production, when they’re slowest and most expensive to fix.

Secrets also needed a single, controlled home across AWS and GCP.

What I built

  • Integrated Snyk, Trivy and SonarQube into the CI/CD workflows as gates, so a failing scan stops the build.
  • Designed secret management with Vault, AWS Secrets Manager and GCP Secret Manager, so credentials never live in code or pipeline config.

How it flows

  1. Commit
  2. Code analysis
  3. Dependency scan
  4. Image scan
  5. Gate
  6. Deploy

Decisions I made and why

Fail the build, don’t file a report

A finding that blocks a merge gets fixed that day. A finding in a report gets fixed eventually.

Block on what can be fixed

Gating on critical issues that have a fix available keeps the signal high. Teams take the gate seriously because it rarely cries wolf.

Secrets come from a manager at runtime

Pulling credentials from Vault or a cloud secret manager means rotation doesn’t require a code change, and nothing sensitive sits in Git.

What changed

Vulnerabilities dropped 35% and code compliance improved, because problems now surface in the pull request instead of in production.

What I’d do next

Sign container images and verify signatures at deploy time, so only images built by the pipeline can run.
