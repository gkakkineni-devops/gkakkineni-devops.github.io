[faster-releases]
title: Faster path to production
summary: Getting ML services from merge to production faster, without making releases riskier.
where: State Farm
when: 2025 to now
role: DevOps Engineer (AWS/GCP)
client: yes
results:
  - 40% | shorter release cycles
  - 99.9% | uptime on the infrastructure underneath
situation:
  - The teams I support build and serve machine learning models across AWS and GCP. Code moved through pipelines on more than one CI system, and environments didn’t always come from the same source of truth.
  - The result was predictable: changes waited longer than they needed to, and every release carried a bit of extra uncertainty because the path to production wasn’t the same every time.
built:
  - Developed and tuned CI/CD pipelines on GitHub Actions, Jenkins and Buildkite, so each service has a clear, repeatable path from commit to production.
  - Provisioned and secured the infrastructure behind those pipelines with Terraform and CloudFormation, so environments are created from code and reviewed like code.
  - Brought ML lifecycle tools, SageMaker, Bedrock and Hugging Face, into the same pipelines so model deployments follow the same rules as application code.
flow:
  - Pull request
  - Build and test
  - Scan
  - Package
  - Deploy with GitOps
  - Monitor
decisions:
  - Meet teams where they are | Moving every team to one CI tool overnight would have stalled delivery. I focused on making each path consistent and fast first, using the tool the team already ran.
  - Infrastructure is reviewed like code | Terraform and CloudFormation changes go through pull requests. That turns environment changes into something people can read, discuss and roll back.
  - Models ship like software | A model deploy gets the same build, scan and rollout steps as a service. Fewer special cases means fewer surprises.
changed: Release cycles got 40% shorter, and the infrastructure provisioned this way held 99.9% uptime.
next: Measure lead time and change failure rate per team as standing metrics, so improvements show up on a dashboard instead of in anecdotes.
stack: GitHub Actions, Jenkins, Buildkite, Terraform, CloudFormation, SageMaker, Bedrock, Hugging Face

card_text: One delivery path for ML services across GitHub Actions, Jenkins and Buildkite, with infrastructure from code.

[zero-downtime-releases]
title: Releases nobody notices
summary: Making deploys on Kubernetes safe enough that users never feel them.
where: State Farm
when: 2025 to now
role: DevOps Engineer (AWS/GCP)
client: yes
results:
  - 95% | fewer interruptions during releases
situation:
  - Every release was a moment of risk. When a change misbehaved, users felt it before anyone could react, and getting back to a good state took manual work under pressure.
  - With high-traffic applications on EKS and GKE, that risk grows with every service and every deploy.
built:
  - Managed EKS and GKE clusters and packaged services with Helm charts.
  - Integrated ArgoCD and FluxCD so the cluster follows what’s in Git, and a rollback is a revert.
  - Implemented blue-green and canary deployment strategies, so new versions get a slice of real traffic before everyone sees them.
  - Set up autoscaling policies for the high-traffic applications so a rollout never competes with load.
flow:
  - Merge to main
  - GitOps sync
  - Canary slice
  - Check health
  - Promote or roll back
decisions:
  - GitOps over pushing from CI | When the cluster pulls its desired state from Git, there’s one source of truth. You can see what’s running, and undoing a change is a normal Git revert instead of a special procedure.
  - Canary for risky services, blue-green for the rest | Canary releases catch problems that only show up under real traffic. Blue-green is simpler when a clean switch is enough. Using both kept the setup no more complex than each service needed.
  - Let a small slice find the problem | A new version that misbehaves is caught while only a few users can see it, and everyone else stays on the version that works. People investigate afterwards, but users stop being affected quickly.
changed: Service interruptions during releases dropped 95%, and releases stopped being something the teams had to schedule around.
next: Tie canary analysis to the same SLOs the teams already watch, so “healthy enough to promote” means exactly what it means in production.
stack: Kubernetes (EKS, GKE), Helm, ArgoCD, FluxCD
extra: Want to see the idea in action? The [deploy playground](@/playground/) runs a small simulation of this setup, including a canary that rolls itself back.

[gpu-platform-for-ml]
title: GPU platform for ML
summary: Giving data scientists the GPU capacity they need, without paying for GPUs nobody is using.
where: State Farm
when: 2025 to now
role: DevOps Engineer (AWS/GCP)
client: yes
results:
  - 30% | faster training and inference
  - 15% | lower cost for GPU workloads
situation:
  - Deep learning workloads need GPUs, and GPUs are both expensive to leave idle and painful to wait for. Data scientists want capacity on demand; the budget wants nothing running that isn’t doing work.
  - On top of training, the teams were moving toward LLM-based applications, which bring their own deployment and serving needs.
built:
  - Orchestrated GPU and TPU-enabled clusters for deep learning workloads across AWS and GCP.
  - Automated resource monitoring and scaling for GPU workloads, so clusters grow for a job and shrink after it.
  - Integrated SageMaker, Bedrock and Hugging Face into the DevOps pipelines and worked with data scientists and ML engineers to deploy LLM-based apps to production.
flow:
  - Training job queued
  - Scale up GPUs
  - Train and track
  - Register model
  - Deploy and serve
  - Scale down
decisions:
  - Scale on the work, not the calendar | Scaling GPU capacity around the actual jobs, instead of keeping a fixed fleet warm, is where most of the savings came from.
  - Measure first, then scale | Automated monitoring of GPU workloads showed when capacity sat idle and when it ran short, so scaling followed real usage instead of guesses.
  - Use managed ML services where they fit | SageMaker, Bedrock and Hugging Face cover a lot of ground. Plugging them into the existing pipelines was faster and safer than rebuilding what they already do.
changed: Training and inference ran up to 30% faster, and automated scaling cut costs for GPU workloads by 15% while keeping performance where it needed to be.
next: Show GPU spend per team and per model, so the people choosing instance sizes can see what their choices cost.
stack: GPU and TPU clusters, Kubernetes (EKS, GKE), SageMaker, Bedrock, Hugging Face

[observability]
title: Seeing problems first
summary: Finding out about issues from a dashboard, not from a support ticket.
where: State Farm
when: 2025 to now
role: DevOps Engineer (AWS/GCP)
client: yes
results:
  - 25% | less downtime
situation:
  - Problems were too often noticed after they reached users. Metrics and logs existed, but they were spread across tools, and alerts didn’t always point at what actually needed attention.
built:
  - Established observability across Prometheus, Grafana, CloudWatch and the ELK stack, so metrics and logs for a service can be read together.
  - Built dashboards and alerts on top of that data, so problems show up before users report them.
  - Handled incident response and root cause analysis, documented lessons learned and followed through on the fixes.
flow:
  - Metrics and logs
  - Dashboards
  - Alert
  - Respond
  - Root cause review
  - Fix and document
decisions:
  - Every alert needs an owner and an action | An alert that nobody acts on trains people to ignore alerts. If it fires, someone should know what to do.
  - Watch trends, not just thresholds | An alert on a trend catches a problem that is getting worse before it crosses the line where users notice.
  - Reviews are about the system | Root cause reviews look for what in the system allowed the problem, then fix that, so the same incident doesn’t come back next month.
changed: Downtime went down 25%, and problems started showing up on a dashboard before they showed up in a support queue.
next: Base alerting on service-level objectives and error budgets for more of the important services, so it follows what users experience.
stack: Prometheus, Grafana, CloudWatch, ELK

home_sub: Prometheus, Grafana, CloudWatch and ELK with alerts that matter
card_result: **25%** less downtime
card_text: Metrics, logs and dashboards in one place, alerts that mean something, and honest root cause reviews.

[security-in-the-pipeline]
title: Security in the pipeline
summary: Keeping secrets out of code, and catching problems in the pull request instead of in production.
where: State Farm, plus my own projects
when: 2025 to now
role: DevOps Engineer (AWS/GCP)
client: yes
results:
  - 3 | secret managers behind one approach
  - Every push | scanned and linted in my own projects
situation:
  - Credentials and compliance rules don’t stop at one cloud. With work on both AWS and GCP, secrets needed a single, controlled way of being handled, and security checks needed to happen before code ships, not after.
built:
  - Set up secrets management with Vault, AWS Secrets Manager and GCP Secret Manager to meet compliance requirements, so credentials don’t live in code or pipeline config.
  - Put scanners in the pipeline as gates. In my own projects, Trivy, hadolint and tflint run on every push and a failing scan stops the build. Snyk and SonarQube are the dependency and code-analysis tools I use in the same position.
flow:
  - Commit
  - Code analysis
  - Dependency scan
  - Image scan
  - Gate
  - Deploy
decisions:
  - Fail the build, don’t file a report | A finding that blocks a merge gets fixed that day. A finding in a report gets fixed eventually.
  - Block on what can be fixed | Gating on critical issues that have a fix available keeps the signal high. Teams take the gate seriously because it rarely cries wolf.
  - Secrets come from a manager at runtime | Pulling credentials from Vault or a cloud secret manager means rotation doesn’t require a code change, and nothing sensitive sits in Git.
changed: Secrets moved into managed stores that help meet compliance requirements, and on my own projects a problem now surfaces in the pull request instead of in production.
next: Sign container images and verify signatures at deploy time, so only images built by the pipeline can run.
stack: Vault, AWS Secrets Manager, GCP Secret Manager, Trivy, hadolint, tflint, Snyk, SonarQube
extra: This website uses the same idea on a small scale: [Trivy and hadolint run on every push](@/work/this-website/), and a failing scan blocks the deploy.
home_num: 3
home_sub: Secret managers behind one approach, and scans that fail builds
card_result: **3** secret managers, one approach
card_text: Secrets out of code, and scans that fail builds instead of filling reports.
card_stack: Vault, Secrets Manager, Trivy, hadolint, Snyk, SonarQube
